Next: Section F — Auto-save

This is the next feature from your original requirements:

“Allow auto save when updating patient information.”

I recommend we implement it as a draft system, not by automatically creating a referral every time the user types.

The workflow would be:

Nurse starts referral → information is automatically saved as a draft → browser closes/network drops → nurse returns → draft can be recovered → nurse completes → Submit Referral.

That is safer for clinical data than continuously inserting incomplete referrals into the main referrals table.

Before we implement F

There is one architectural decision we should make:

Option 1 — Browser draft

  • Saves temporarily in the browser.

  • Very simple.

  • Useful if the same device is used.

  • Does not require a new Supabase table.

Option 2 — Supabase draft

  • Saves the draft securely to the database.

  • Can potentially be recovered from another device/session.

  • Better for a serious healthcare system.

  • Requires a proper draft mechanism/table and RLS policies.

For REFLINK as a government-facing healthcare innovation, I recommend Option 2, but we should design the database properly before coding it.

So the next step should be:

F1 — Design the secure draft/autosave database structure and RLS policy.

We should not start coding F yet until we establish that structure, because patient information is sensitive clinical data and we don't want an autosave feature accidentally creating an RLS/privacy vulnerability.

F1 — Secure draft/autosave database design

Yes. For REFLINK, I recommend Supabase-based drafts, not browser-only drafts. Because the draft may contain patient identifiers, contact information, clinical findings and diagnoses, it should be protected by RLS just like the rest of the application. Supabase specifically recommends enabling RLS on exposed tables and using auth.uid() to restrict rows to the authenticated user. Supabase+1

What we are going to build

The workflow will eventually be:

New Referral opened
→ nurse enters information
→ REFLINK automatically saves draft
→ internet/browser interruption
→ nurse returns
→ Restore Draft
→ continues filling
→ Submit Referral
→ draft is marked completed/deleted
→ final record goes into referrals.

I recommend not putting incomplete referrals directly into referrals. Drafts should be separate.

F1.1 — Create the draft table

Go to:

Supabase → SQL Editor → New Query

Run this entire SQL:

SQL
CREATE TABLE IF NOT EXISTS public.referral_drafts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),

  user_id uuid NOT NULL
    REFERENCES auth.users(id)
    ON DELETE CASCADE,

  facility_id uuid NULL
    REFERENCES public.facilities(id)
    ON DELETE SET NULL,

  draft_data jsonb NOT NULL DEFAULT '{}'::jsonb,

  created_at timestamptz NOT NULL DEFAULT now(),

  updated_at timestamptz NOT NULL DEFAULT now()
);

Why jsonb?

The draft contains a variable set of form fields. jsonb lets us save the current form state as one structured object while we are still evolving the referral form. Supabase recommends jsonb for variable/unstructured data, while structured relational fields should remain relational where appropriate. Supabase

For example, the draft can contain:

patient_identifier
patient_phone
patient_address
relative_name
relative_relationship
relative_phone
diagnosis_status
diagnosis_category
provisional_diagnosis
investigation_category
investigations
...

We are not changing your referrals table for this.

F1.2 — Add indexes

Immediately underneath the table creation, run:

SQL
CREATE INDEX IF NOT EXISTS referral_drafts_user_id_idx
ON public.referral_drafts(user_id);

CREATE INDEX IF NOT EXISTS referral_drafts_facility_id_idx
ON public.referral_drafts(facility_id);

CREATE INDEX IF NOT EXISTS referral_drafts_updated_at_idx
ON public.referral_drafts(updated_at DESC);

The user index is particularly important because our RLS and application queries will identify drafts by user_id. Supabase recommends indexing columns used by RLS policies. Supabase

F1.3 — Enable RLS

Run:

SQL
ALTER TABLE public.referral_drafts
ENABLE ROW LEVEL SECURITY;

This is essential. A table created through SQL does not automatically get the same protection you should assume from the dashboard; Supabase explicitly recommends enabling RLS for exposed tables. Supabase

F1.4 — Create SELECT policy

Run:

SQL
CREATE POLICY "Users can view their own referral drafts"
ON public.referral_drafts
FOR SELECT
TO authenticated
USING (
  (select auth.uid()) = user_id
);

This means:

A logged-in user can only retrieve their own drafts.

F1.5 — Create INSERT policy

Run:

SQL
CREATE POLICY "Users can create their own referral drafts"
ON public.referral_drafts
FOR INSERT
TO authenticated
WITH CHECK (
  (select auth.uid()) = user_id
);

This prevents an authenticated user from creating a draft belonging to another user.

Supabase's RLS documentation specifically uses WITH CHECK for validating values on INSERT. Supabase

F1.6 — Create UPDATE policy

Run:

SQL
CREATE POLICY "Users can update their own referral drafts"
ON public.referral_drafts
FOR UPDATE
TO authenticated
USING (
  (select auth.uid()) = user_id
)
WITH CHECK (
  (select auth.uid()) = user_id
);

This is important.

It means the nurse can update their own draft, but cannot change the draft's user_id to somebody else.

Supabase recommends using both USING and WITH CHECK for secure UPDATE policies. Supabase

F1.7 — Create DELETE policy

When the referral is finally submitted, we can remove the draft.

Run:

SQL
CREATE POLICY "Users can delete their own referral drafts"
ON public.referral_drafts
FOR DELETE
TO authenticated
USING (
  (select auth.uid()) = user_id
);

F1.8 — Grant authenticated access

Run:

SQL
GRANT SELECT, INSERT, UPDATE, DELETE
ON public.referral_drafts
TO authenticated;

RLS determines which rows the user can access; PostgreSQL grants determine whether the role can access the table at all. These are separate layers. Supabase

F1.9 — Automatically update updated_at

We want to know when the draft was last saved.

Create this function:

SQL
CREATE OR REPLACE FUNCTION public.update_referral_draft_timestamp()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$;

Then:

SQL
DROP TRIGGER IF EXISTS referral_draft_updated_at
ON public.referral_drafts;

CREATE TRIGGER referral_draft_updated_at
BEFORE UPDATE ON public.referral_drafts
FOR EACH ROW
EXECUTE FUNCTION public.update_referral_draft_timestamp();

Now every time REFLINK autosaves a draft, updated_at automatically changes.
