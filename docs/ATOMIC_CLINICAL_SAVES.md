# Atomic clinical saves — review candidate

Hosted status update (17 November 2026): the two atomic migrations are installed in synthetic staging, the six-point structural preflight passes, and the branch-specific preview enables the two atomic flags against staging only. See HOSTED_STAGING_INSTALLATION_2026-11-17.md. Production remains NO-GO. Earlier review-only/unapplied statements below describe the pre-installation stage and must not be interpreted as current hosted status.

The proposed `database/changes/atomic_clinical_updates.sql` adds a transaction for receiving assessment, admission and discharge saves. It locks the authorized referral, compares a complete clinical snapshot, validates an allowlisted patch, records an idempotent operation and executes existing audit triggers in one transaction. Response projections exclude patient identity fields. Active account/session, receiving role, facility and password-reset checks run on replay as well as first save.

Apply only after the investigation candidate in an isolated rehearsal. This file is not an applied migration. Its direct-write trigger rejects legacy frontend clinical writes. The frontend adapter is now integrated behind `VITE_ATOMIC_CLINICAL_SAVES_ENABLED=true`; the default is disabled. Do not apply this changeset to a hosted environment before the adapter and flag are rehearsed together. Production behaviour is unchanged while the flag is absent.

The adapter projects complete expected snapshots and allowlisted patches into the RPC body, strips client lifecycle status/timestamps (except explicit admission time), validates the response projection and never falls back to direct writes after an RPC error. Conflicts preserve the form; uncertain outcomes use the existing per-referral pause and administrator review. An operation UUID is generated per explicit save attempt. No automatic retry, persistent operation queue or cross-device reconciliation is claimed. Existing preflight reads remain as an early warning; the transaction is the authoritative conflict check.

`tests/database/clinical_contracts.py` first runs the investigation contracts, then adds synthetic clinical columns and tests concurrent assessment edits, replay, admission/discharge lifecycle, authorization, validation, rollback and direct-write denial. The fixture is not a complete Supabase/RLS/storage rehearsal. Existing audit triggers must be inspected against the actual baseline before promotion. This change does not implement privileged corrections or attachment reconciliation.

Release work still required: authenticated staging workflow tests; migration-history reconciliation; clinical review; rollback rehearsal. During a coordinated maintenance window, rehearse the backend and flag-enabled build together; legacy clients will be denied by the new write guard. Never enable the client flag before the backend is verified. Do not roll the frontend back to direct writes while retaining the guard; rehearse a coordinated rollback without removing clinical data or operation history. Neither hosted database nor production is changed by these tests.
