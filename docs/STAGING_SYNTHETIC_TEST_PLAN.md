# REFLINK synthetic staging test plan

**Status:** specification only — no Auth users, database rows, secrets or schema objects have been created by this plan.
**Target:** Supabase project `reflink-synthetic-staging` (`rcskuzmvyugbanygizri`), region `eu-west-2`.
**Data rule:** synthetic records only. Never copy production patients, referrals, staff, contact details, identifiers, exports or backups into staging.

## 1. Preconditions

Do not execute this plan until the authoritative schema baseline has been recovered or reconstructed from an approved schema-only export, reviewed, and successfully applied to this isolated project. Confirm all required schemas, extensions, types, tables, constraints, triggers, views, RLS policies, grants and function dependencies. Use separate staging-only Supabase credentials and Vercel environment variables. Never reuse production service-role keys, JWT secrets, database passwords, SMS credentials or storage credentials.

## 2. Synthetic facility and identity matrix

Use reserved, clearly synthetic names and non-routable contact values. Do not use real staff names, personal email addresses or live phone numbers.

| Fixture | Facility | User role | Facility assignment | Purpose |
|---|---|---|---|---|
| F-A | SYNTHETIC-PHC-A | PHC staff | F-A | Create and refer patients |
| F-B | SYNTHETIC-GENERAL-B | Receiving staff | F-B | Receive and manage referrals addressed to F-B |
| F-C | SYNTHETIC-GENERAL-C | Receiving staff | F-C | Negative cross-facility authorization tests |
| U-ADMIN | Synthetic administrator | Administrator | No facility or approved admin assignment | Administrator-only reporting and administration |
| U-UNASSIGNED | Synthetic receiving user | Receiving staff | No facility | Missing-assignment denial tests |
| U-PHC-B | Synthetic PHC user | PHC staff | F-B | Wrong-role denial at a receiving facility |

The fixture IDs should be generated by the staging database/Auth system. Do not hard-code generated UUIDs into reusable seed migrations.

## 3. Referral scenario matrix

Create referrals only after the exact live status constraint and required fields are reproduced in staging. Include:

- R-NEW: routine referral sent to F-B.
- R-URGENT: urgent referral sent to F-B with a synthetic acknowledgement deadline.
- R-ACK: acknowledged referral.
- R-ARRIVED: patient-arrival recorded.
- R-ASSESS: assessment in progress.
- R-ADMITTED: admitted referral.
- R-DISCHARGED: discharged referral eligible for counter-referral.
- R-COMPLETE: completed referral with structured counter-referral.
- R-CANCEL: cancelled referral.
- R-TEST: explicitly marked synthetic test referral, excluded from operational aggregate reporting where the RPC contract requires it.
- R-CROSS-FACILITY: referral for F-C, used to prove F-B users cannot access or mutate another facility's referrals.
- R-EDGE-DATES: records at Africa/Lagos month boundaries for reporting window tests.

No fixture should contain real patient identifiers, diagnoses copied from records, free-text clinical narratives, addresses or real phone numbers. Use clearly artificial labels and neutral test-only values.

## 4. Authorization and RLS tests

For every exposed table, RPC, view and storage policy, test anonymous, PHC staff, receiving staff at the correct facility, receiving staff at the wrong facility, administrator and service-role behavior. Assert both allowed and denied operations. Specifically test direct PostgREST/RPC access, not only hidden or disabled UI controls.

- PHC user can create and view only permitted referrals from F-A.
- Receiving user at F-B can access only referrals assigned to F-B under the approved policy.
- Receiving user at F-C cannot read or mutate F-B referrals.
- PHC user cannot invoke receiving-only counter-referral completion.
- Receiving user cannot complete a referral assigned to another facility.
- Non-admin identities cannot call administrator aggregate RPCs.
- Anonymous users cannot call authenticated clinical RPCs.
- Browser roles cannot read private outbox or attempt-ledger tables or invoke service-only queue functions.
- Authenticated inbox access is owner-scoped and mutation-limited.
- No policy is broadened merely to make a test pass; update the access model and review it first.

## 5. Lifecycle, concurrency and notification tests

- Exercise valid referral transitions and reject invalid transitions.
- Verify counter-referral requirement before completion.
- Submit duplicate counter-referrals concurrently and confirm exactly one succeeds.
- Exercise concurrent print logging and ensure per-referral print numbering cannot duplicate after the appropriate safe fix is designed and reviewed.
- Verify stale conditional updates fail without overwriting a newer referral state.
- Verify acknowledgement deadline behavior at relevant urgency and time boundaries.
- Verify notification outbox idempotency, lease fencing, retry bounds, expiry, dead-letter and attempt audit behavior.
- Verify referral lifecycle changes cancel only stale reminder work.
- Keep user-addressed enqueue disabled until an authoritative notification-duty roster and eligibility policy are approved.
- Do not enable SMS, email or external provider dispatch in the initial integration suite.

## 6. Public-health aggregate and disclosure tests

Use synthetic cohorts with counts 0, 1, 2, 3, 4, 5 and larger values. Test primary and complementary suppression across every reporting RPC, adjacent time windows, overlapping filters, facility grouping and combined totals. Include empty periods, missing timestamps, invalid date ranges, month boundaries and test referrals.

The acceptance criterion is not simply that each individual function suppresses small cells. The combined reporting surface must resist differencing across RPCs and periods. Outputs must be labelled as recorded referral activity, not population incidence, disease prevalence, unmet need, care quality or service performance unless separately validated with appropriate denominators and governance approval.

## 7. Execution record template

For each test batch, record:

- Git commit and migration version(s)
- Staging project reference and environment
- Synthetic fixture version
- Test identity role/facility
- SQL/API operation and expected result
- Actual result and sanitized error
- RLS/grant/advisor evidence
- Cleanup result
- Reviewer and date

Never include access tokens, passwords, patient data, production identifiers or provider secrets in test logs or CI artifacts.

## 8. Exit criteria

Staging validation is complete only when the baseline and all proposed migrations replay from an empty database, all tests above pass with independent synthetic identities, advisors have no unresolved high-risk findings, migration order and rollback/recovery are documented, and database/security plus clinical governance reviewers approve the release evidence. A clean advisor scan on an empty database is not an acceptance result.
